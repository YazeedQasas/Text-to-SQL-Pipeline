The bug that had to be fixed to make it work

The single-chat code patched turns[turns.length - 1] — the last turn of whatever was on screen. Correct only while there is one chat and it is the visible one. With several, switching tabs mid-answer wrote one chat's tokens into another.

Found while tracing

Four cache bugs

Each one was reproduced against real code before being called a bug, and each fix was verified by re-running the same reproduction.

What could happen Before After
المدعى (the sued) served the SQL cached for المدعي (plaintiff) Two opposite parties to a case, one hash. served blockedSplit normalizer — keys stop folding ى→ي and ة→ه.
A chat deep in one subject ran SQL built for another chat's cold opening The key is the question alone — no chat id, no history. served blockedQUERY_CACHE_FOLLOW_UPS now defaults false.
CONTEXT_MAX_TURNS=0 silently turned "store first turns only" into "store everything" A context knob reaching cache policy. 0 reads as "unlimited"; it means "no memory". stored blockedCache policy now derives from untrimmed input.
An anaphoric question written to the cache from a first turn The write gate checks turn position, never question content. stored containedStill stored, but only another first turn can read it — and that has no context to contradict.

All four reproductions, re-run against the fixed code

QUERY_CACHE_FOLLOW_UPS = False

1  anaphoric written from a first turn      True    (unchanged, by design)
2  chat B reads chat A's cold-start SQL     False   ← was True
3  المدعى served المدعي SQL                  False   ← was True
4  CONTEXT_MAX_TURNS=0 stores a follow-up   False   ← was True

The rule that came out of it

One bug wearing four coats

“Every caching problem here is the same bug — two different questions get treated as the same because the thing that made them different got erased. Semantic does it with vectors, the normalizer does it with Arabic folding. Same crime, different spot.”

That is now written into query_cache.py's module docstring, because it is the argument that should stop the next widening of the key. The module already rejected semantic matching for exactly this reason and then shipped the lexical version of the same mistake.

What the split actually does

Two normalizers, because the callers fail differently. A false merge in search is one weak candidate a threshold rejects. A false merge in a key is the wrong stored query running and reporting a confident number.

services/arabic.py

normalize()      // soft, for search — mirrors the DB's *_norm columns
    NFC · diacritics · tatweel · hamza carriers
    + ى→ي  ة→ه          ← merges distinct words
    + definite article

normalize_key()  // strict, for cache keys
    NFC · diacritics · tatweel · hamza carriers
    + definite article        ← the case the cache was built for:
                                القضايا المدورة → قضايا مدورة

Evidence for dropping both folds, not just ى→ي: كتابة العقد (drafting the contract) collided with كتابه العقد (his contract book), and محاكمة المتهم (the trial) with محاكمه (his court). The cost is real and accepted — شكوى and شكوي are one word spelled two ways and now key differently. That is a hit given up to stop serving the plaintiff's query for a question about the defendant.

Open

Still outstanding

  • Cache hits skip the 413 context guard. Measured at 2,377 tokens against a 200-token budget — 11.9× over, HTTP 200. Three-line fix, not applied. Practically unreachable while follow-up reads are off, because overflowing the window needs history and a cache hit now needs none; it returns the moment QUERY_CACHE_FOLLOW_UPS goes back to true.
  • The UI is unverified. No browser automation available here, so the React wiring rests on a clean build and a proven API contract. The case worth clicking is the one the old code got wrong: start an answer, switch chats while it streams, come back.
  • Hit rate will drop, possibly a lot. First-turn-only reads mean a long chat full of unrelated self-contained questions gets no hits after its first. The counters in the Cache panel are the thing to watch before deciding whether to turn follow-up reads back on.
  • ة→ه removal was one step past what was asked. Easy to put back if the lost hits matter more than the collision.

Action

Yours

  • Nothing is committed. All of it sits in the working tree on redis-question-cache.
  • Check CONTEXT_WINDOW_TOKENS matches LM Studio. It is set now, but it has to equal the context length the model is actually loaded with. Set it higher and a full chat stops failing cleanly: LM Studio truncates the start of the prompt, which is the schema, and the model answers with invented columns.
  • Decide on the 413 guard. Applying it means a chat at its limit can no longer be answered even from cache — the cheapest turn becomes the refused one. Consistent with the design's stated position, but a behaviour change.
